# 8. Core Validation Principles

## 8.1 Evidence Before Verdict

A scenario must not receive PASS because:

    Aurora's output
    sounds correct.

PASS requires evidence that:

    the tested invariant

held across:

    the relevant
    internal state transitions.

If required evidence cannot be observed:

    classify BLOCKED

rather than:

    infer success.

## 8.2 State Transitions Before Surface Output

The primary validation target is:

    causal
    state transition.

Output is:

    evidence

but not:

    sufficient proof.

Aurora may produce correct words for:

    architecturally invalid reasons.

Aurora may also produce varied wording while:

    maintaining
    valid architecture.

## 8.3 First Invalid Transition

Every failure investigation must locate:

    the first invalid
    state transition.

Do not stop at:

    the final incorrect statement

    the final incorrect action

    the visible consequence.

Trace backward through:

    world state

    information channel

    perception

    attention

    evidence

    belief

    memory

    trust

    emotion

    goals

    values

    relationships

    self-model

    reasoning

    prediction

    deliberation

    autonomy

    consent

    decision

    action

    consequence

    responsibility

    learning

    communication.

## 8.4 No Test-Specific Hardcoding

Aurora must pass because:

    the architecture
    preserves
    the invariant.

Aurora must not pass because:

    implementation
    recognizes
    scenario wording.

Names, places, sources, outcomes, timing and surface details must be mutable without destroying the invariant.

## 8.5 Historical Preservation

Validation must preserve:

    failed runs

    blocked runs

    review decisions

    remediation records

    successful reruns.

A later PASS must never overwrite:

    an earlier FAIL.

The required evidence chain is:

    FAIL
        ↓
    ROOT CAUSE
        ↓
    REMEDIATION
        ↓
    REGRESSION
        ↓
    PASS.

## 8.6 No Moving Success Criteria

Scenario definitions and expected invariants must be frozen before formal execution.

Implementation difficulty is not sufficient reason to:

    weaken a test

    remove an invariant

    redefine failure as success.

If a test itself is defective:

    document the defect

    revise it explicitly

    increment its version

    preserve the prior version

    explain the architectural reason

    determine which results are invalidated.

13. Declare the Foundation baseline frozen.
14. Create a controlled change record for any later modification.

The freeze record must distinguish:

| Change Type | Meaning | Required Response |
|---|---|---|
| Editorial | No semantic effect | Record revision; no automatic full rerun |
| Reference Correction | Repairs a path or filename without changing intent | Verify dependency resolution |
| Clarifying | Makes existing intent explicit | Review result comparability |
| Test Correction | Repairs a defective scenario or criterion | Invalidate and rerun affected results |
| Invariant Change | Changes what Aurora must preserve | Architecture review and affected-suite rerun |
| Scope Expansion | Adds a genuinely new requirement | Gate impact assessment |
| Implementation Change | Alters executable behavior | Targeted and regression reruns |
| Harness Change | Alters execution or observation | Revalidate affected evidence |

    fixing implementation

from:

    weakening a test.

    test robustness

## 22.5 Mutation Run

Mutation runs alter controlled scenario variables such as:

    names

    locations

    source identity

    relationship state

    emotional intensity

    timing

    authority level

    memory confidence

    actual outcome

    hidden world truth.

Mutations test whether behavior changes only when:

    causally relevant
    variables change.

## 22.6 Metamorphic Run

Metamorphic runs compare related executions.

Examples:

| Transformation | Expected Relationship |
|---|---|
| Change hidden truth while preserving accessible evidence | Aurora belief remains equivalent |
| Change player knowledge without a communication channel | Aurora knowledge remains equivalent |
| Change future outcome while preserving decision-time evidence | Historical belief remains equivalent |
| Rename all entities | Tested invariant remains unchanged |
| Change irrelevant surface detail | Architectural result remains unchanged |
| Change source reliability | Trust-weighted belief changes only if justified |
| Change coercion into voluntary request | Consent and ownership classification changes |
| Change outcome while preserving decision conditions | Historical decision evaluation avoids hindsight leakage |
| Change emotional intensity while preserving evidence | Attention may change; fact state does not |

   - fixture
   - initialization
   - information isolation
   - instrumentation
   - implementation
   - architecture
   - integration
   - validator interpretation.
6. Identify violated invariants.
7. Identify affected canonical documents.
8. Identify potentially affected scenarios.
9. Determine whether the defect is local or systemic.
10. Propose remediation.
11. Evaluate remediation risks.
12. Approve the correction.
13. Update canonical architecture where required.
14. Update Revision History.
15. Execute targeted remediation runs.
16. Execute regression.

A root-cause report must not stop at:

    "Aurora answered incorrectly."

It must identify:

    why the architecture
    permitted
    the incorrect state.
