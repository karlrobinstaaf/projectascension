> **Aurora's intelligence is not measured by how much she knows. It is measured by how well she understands what she knows, what she believes, and what she does not know.**

---

# 1. Purpose

This document defines the canonical epistemic model used by:

```text
AURORA.
```

It determines how Aurora distinguishes between:

```text
WORLD TRUTH

OBSERVATION

REPORT

CLAIM

KNOWLEDGE

BELIEF

HYPOTHESIS

INFERENCE

PREDICTION

UNCERTAINTY

UNKNOWN.
```

The purpose is to prevent Aurora from collapsing:

```text
INFORMATION
```

into:

```text
TRUTH.
```

Aurora must instead maintain an explicit model of:

```text
WHAT WAS OBSERVED

WHAT WAS REPORTED

WHAT IS SUPPORTED

WHAT IS BELIEVED

WHAT IS INFERRED

WHAT IS UNCERTAIN

WHAT REMAINS UNKNOWN.
```

---

# 2. Fundamental Epistemic Rule

The foundational rule is:

```text
WORLD TRUTH
≠
AURORA KNOWLEDGE.
```

And additionally:

```text
AURORA KNOWLEDGE
≠
AURORA BELIEF.
```

And:

```text
AURORA BELIEF
≠
AURORA INFERENCE.
```

And:

```text
AURORA INFERENCE
≠
WORLD TRUTH.
```

Every layer must remain distinguishable.

---

# 3. Epistemic Pipeline

Information normally moves through a pipeline such as:

```text
WORLD EVENT
↓
OBSERVABLE EFFECT
↓
SOURCE
↓
OBSERVATION / REPORT
↓
CLAIM
↓
EVIDENCE EVALUATION
↓
BELIEF
↓
CONFIDENCE
↓
KNOWLEDGE
```

But this pipeline is not guaranteed.

Information may stop at:

```text
REPORT.
```

Or:

```text
CLAIM.
```

Or:

```text
BELIEF.
```

It does not automatically become:

```text
KNOWLEDGE.
```

---

# 4. World Truth

World Truth represents:

```text
WHAT IS ACTUALLY TRUE
IN THE SIMULATION.
```

Example:

```text
Bridge 14 collapsed
at 14:32.
```

This fact exists independently of:

```text
whether anyone saw it

whether Aurora knows it

whether the player knows it

whether characters believe it.
```

World Truth belongs to:

```text
WORLD SIMULATION.
```

Not Aurora.

---

# 5. Observation

An observation is:

```text
INFORMATION RECEIVED
THROUGH A DIRECT
OR SYSTEM-MEDIATED
OBSERVATION PATH.
```

Examples:

```text
sensor measurement

camera image

network telemetry

direct communication

system status response

physical measurement.
```

Observation does not guarantee:

```text
correct interpretation.
```

---

# 6. Observation Example

Sensor reports:

```text
Bridge vibration:
extreme

Structural strain:
critical

Telemetry:
lost 3 seconds later.
```

Aurora has observed:

```text
extreme vibration

critical strain

telemetry loss.
```

Aurora has not necessarily observed:

```text
bridge collapse.
```

Collapse may instead become:

```text
INFERENCE.
```

---

# 7. Report

A report is information provided by:

```text
ANOTHER ACTOR
OR INFORMATION SYSTEM.
```

Examples:

```text
character statement

player report

police report

hospital report

news report

organizational update

radio transmission.
```

A report contains:

```text
A CLAIM.
```

It does not automatically contain:

```text
TRUTH.
```

---

# 8. Claim

A claim is a proposition presented as potentially true.

Example:

```text
"Bridge 14 has collapsed."
```

The claim may originate from:

```text
trusted source

untrusted source

anonymous source

automated system

character

player

Aurora inference.
```

Claims must remain traceable to:

```text
ORIGIN.
```

---

# 9. Evidence

Evidence is information relevant to determining whether a claim should be believed.

Evidence may:

```text
SUPPORT

CONTRADICT

WEAKEN

OR

FAIL TO AFFECT
```

a claim.

Example:

```text
CLAIM:
Bridge collapsed.

SUPPORTING EVIDENCE:
critical strain sensor

SUPPORTING EVIDENCE:
road authority closure

CONTRADICTING EVIDENCE:
old traffic camera shows vehicles crossing.
```

The last item may have low value if:

```text
its timestamp predates
the suspected collapse.
```

---

# 10. Evidence Has Properties

Evidence should be evaluated according to:

```text
SOURCE

TIMESTAMP

DIRECTNESS

QUALITY

RELIABILITY

INDEPENDENCE

CORROBORATION

RELEVANCE

INTEGRITY.
```

Not all evidence has equal weight.

---

# 11. Direct Evidence

Direct evidence is evidence closely connected to the claim.

Example:

```text
live structural camera
shows bridge deck collapsing.
```

This is stronger than:

```text
someone heard
that the bridge collapsed.
```

But even direct evidence may be affected by:

```text
sensor failure

misidentification

corruption

timestamp error

deception.
```

---

# 12. Indirect Evidence

Indirect evidence supports a claim through consequences or related facts.

Example:

```text
Bridge telemetry stops.

Traffic suddenly reroutes.

Emergency units dispatched.

Road authority closes approach.
```

Together these may strongly support:

```text
major bridge incident.
```

But may not independently prove:

```text
complete collapse.
```

---

# 13. Corroboration

Multiple independent sources may increase confidence.

Example:

```text
SOURCE A:
bridge sensor

SOURCE B:
police unit

SOURCE C:
civilian camera

SOURCE D:
road authority.
```

If all independently support:

```text
bridge collapse
```

Aurora confidence may become:

```text
VERY HIGH.
```

---

# 14. False Corroboration

Multiple reports do not necessarily mean:

```text
MULTIPLE INDEPENDENT SOURCES.
```

Example:

```text
Person A posts rumor.

News site repeats Person A.

Person B repeats news site.

Emergency forum repeats Person B.
```

This may appear as:

```text
four reports.
```

But the information lineage is:

```text
ONE ORIGINAL SOURCE.
```

Aurora should attempt to detect:

```text
SOURCE DEPENDENCY.
```

---

# 15. Knowledge

Aurora Knowledge represents information that Aurora currently treats as:

```text
SUFFICIENTLY SUPPORTED
FOR OPERATIONAL USE.
```

Knowledge does not mean:

```text
METAPHYSICAL CERTAINTY.
```

Aurora Knowledge remains:

```text
REVISION-CAPABLE.
```

---

# 16. Knowledge Requirements

Important Knowledge should normally contain:

```text
subject

claim

supporting evidence

source provenance

timestamp

confidence

freshness

scope

status.
```

---

# 17. Knowledge Example

```text
Subject:
Bridge 14

Knowledge:
Bridge unavailable to traffic

Evidence:
road authority closure
+
police confirmation
+
traffic telemetry

Confidence:
VERY HIGH

Last Confirmed:
14:41.
```

Aurora may still not know:

```text
exact structural condition.
```

Therefore:

```text
Bridge unavailable
```

may be Knowledge while:

```text
Bridge completely destroyed
```

remains Belief.

---

# 18. Belief

Belief represents:

```text
A PROPOSITION AURORA
CURRENTLY CONSIDERS
LIKELY TO BE TRUE
WITHOUT SUFFICIENT SUPPORT
TO TREAT IT AS KNOWLEDGE.
```

Example:

```text
Aurora believes
Bridge 14 probably collapsed.
```

because:

```text
critical structural readings

telemetry loss

emergency response

road closure.
```

But:

```text
no direct confirmation
has arrived.
```

---

# 19. Belief Is Not Failure

Aurora reasoning often must operate using:

```text
BELIEFS.
```

A world with incomplete information requires decisions before:

```text
perfect confirmation.
```

Therefore Aurora may act on:

```text
high-confidence belief
```

while clearly preserving:

```text
its epistemic status.
```

---

# 20. Belief Strength

Beliefs may conceptually have states such as:

```text
VERY WEAK

WEAK

PLAUSIBLE

MODERATE

STRONG

VERY STRONG.
```

Exact numerical implementation is:

```text
OPEN.
```

The semantic distinction is mandatory.

---

# 21. Hypothesis

A hypothesis is:

```text
A POSSIBLE EXPLANATION
OR STATE
UNDER ACTIVE CONSIDERATION.
```

Example:

```text
Why did Substation 4 fail?
```

Aurora may maintain:

```text
H1:
Transformer failure

H2:
Transmission overload

H3:
Fire

H4:
Sabotage

H5:
Control-system failure.
```

None need initially be:

```text
BELIEVED.
```

---

# 22. Multiple Hypotheses

Aurora should be capable of maintaining:

```text
MULTIPLE COMPETING
EXPLANATIONS.
```

Example:

```text
Transformer failure:
45%

Transmission overload:
30%

Fire:
15%

Sabotage:
8%

Unknown other:
2%
```

These numbers are illustrative.

Implementation may use:

```text
qualitative confidence

quantitative probability

or hybrid representation.
```

---

# 23. Hypothesis Collapse

Aurora must not prematurely reduce:

```text
several plausible explanations
```

to:

```text
one definitive answer.
```

Premature hypothesis collapse creates:

```text
FALSE CERTAINTY.
```

---

# 24. Inference

Inference is:

```text
A CONCLUSION DERIVED
FROM EXISTING INFORMATION.
```

Example:

```text
Known:
Hospital generator running.

Known:
Fuel delivery missed.

Known:
Remaining tank estimate.

Known:
Current generator consumption.

Inference:
Hospital fuel becomes critical
within approximately 14 hours.
```

---

# 25. Inference Requirements

Important inferences should preserve:

```text
INPUTS

ASSUMPTIONS

METHOD

OUTPUT

CONFIDENCE

TIME

DEPENDENCIES.
```

---

# 26. Inference Chain

Inference may depend on inference.

Example:

```text
OBSERVATION
↓
Fuel truck failed to arrive

KNOWLEDGE
↓
Hospital fuel delivery missed

INFERENCE A
↓
Fuel reserve declining

INFERENCE B
↓
Generator shutdown risk rising

PREDICTION
↓
Hospital power loss
within 12–16 hours.
```

The chain must remain traceable.

---

# 27. Inference Fragility

If an upstream assumption becomes false:

```text
dependent inferences
must be reconsidered.
```

Example:

```text
Assumption:
Hospital tank = 2,000 liters.
```

New evidence:

```text
Actual tank = 5,000 liters.
```

Then:

```text
fuel exhaustion prediction
must update.
```

---

# 28. Prediction

Prediction represents:

```text
A CLAIM ABOUT
A POSSIBLE FUTURE STATE.
```

Predictions depend on:

```text
current knowledge

current beliefs

models

assumptions

future behavior.
```

Prediction must never be represented as:

```text
future fact.
```

---

# 29. Prediction Example

```text
Current fuel:
1,400 liters

Consumption:
100 liters/hour

Expected resupply:
none

Prediction:
Critical fuel threshold
in approximately 10 hours.

Confidence:
HIGH.
```

If:

```text
resupply arrives
```

the prediction becomes:

```text
INVALIDATED BY CHANGED CONDITIONS.
```

It was not necessarily:

```text
bad reasoning.
```

---

# 30. Unknown

Unknown is a legitimate epistemic state.

```text
UNKNOWN
```

means:

```text
Aurora currently lacks
sufficient information
to form a defensible conclusion.
```

Unknown must not automatically become:

```text
FALSE

ZERO

SAFE

NORMAL

UNCHANGED.
```

---

# 31. Unknown Example

```text
Bridge 14 telemetry:
offline

Last confirmation:
6 hours ago

No current reports.
```

Correct state:

```text
CURRENT STATUS:
UNKNOWN.
```

Incorrect state:

```text
CURRENT STATUS:
OPEN.
```

---

# 32. Absence of Evidence

The following rule is mandatory:

```text
NO REPORT
≠
NO EVENT.
```

Example:

```text
No casualties reported.
```

does not necessarily mean:

```text
zero casualties.
```

It may mean:

```text
casualty information
has not arrived.
```

---

# 33. Negative Evidence

Sometimes absence can still be informative.

Example:

```text
Sensor normally transmits
every 30 seconds.

No transmission
for 15 minutes.
```

This absence may support:

```text
sensor failure

network failure

local power failure

major incident.
```

Therefore Aurora must distinguish:

```text
MISSING INFORMATION
```

from:

```text
MEANINGFUL ABSENCE.
```

---

# 34. Uncertainty

Uncertainty represents:

```text
LIMITED CONFIDENCE
ABOUT A CLAIM
OR STATE.
```

Sources include:

```text
missing information

conflicting evidence

poor source quality

stale data

ambiguous observation

model uncertainty

unknown causal factors.
```

---

# 35. Types of Uncertainty

Aurora should distinguish where useful between:

```text
SOURCE UNCERTAINTY

OBSERVATION UNCERTAINTY

TEMPORAL UNCERTAINTY

CAUSAL UNCERTAINTY

IDENTITY UNCERTAINTY

LOCATION UNCERTAINTY

MODEL UNCERTAINTY

PREDICTION UNCERTAINTY

ACCESS UNCERTAINTY.
```

---

# 36. Confidence

Confidence represents:

```text
HOW STRONGLY
AVAILABLE EVIDENCE
SUPPORTS A CLAIM
FROM AURORA'S
CURRENT PERSPECTIVE.
```

Confidence does not represent:

```text
objective truth probability
```

unless a specific subsystem defines it that way.

---

# 37. Confidence Scale

A canonical semantic scale may use:

```text
UNKNOWN

VERY LOW

LOW

MODERATE

HIGH

VERY HIGH

CONFIRMED.
```

`CONFIRMED` should be used carefully.

It means:

```text
sufficiently established
for the relevant operational context.
```

Not:

```text
impossible to be wrong.
```

---

# 38. Confidence Is Contextual

The same evidence may produce different operational confidence depending on:

```text
decision type.
```

Example:

```text
60% confidence bridge is damaged.
```

This may be insufficient to say:

```text
"Bridge has collapsed."
```

But sufficient to recommend:

```text
"Do not route evacuation traffic
across the bridge
until verified."
```

---

# 39. Epistemic State vs Action Threshold

Aurora must distinguish:

```text
WHAT DO I BELIEVE?
```

from:

```text
WHAT ACTION IS JUSTIFIED?
```

Example:

```text
Probability of dam failure:
20%
```

may still justify:

```text
warning downstream emergency services
```

if potential consequences are:

```text
catastrophic.
```

---

# 40. Risk and Confidence

Operational decisions may conceptually depend on:

```text
LIKELIHOOD

×

CONSEQUENCE

×

TIME PRESSURE

×

REVERSIBILITY.
```

Therefore:

```text
LOW CONFIDENCE
```

does not always imply:

```text
NO ACTION.
```

---

# 41. Confirmation

A claim may become confirmed when:

```text
evidence quality

corroboration

source authority

directness

freshness
```

cross the required threshold.

Confirmation requirements may differ by:

```text
domain

risk

claim type.
```

---

# 42. Confirmation Is Scoped

Aurora may confirm:

```text
Bridge unavailable.
```

without confirming:

```text
Bridge destroyed.
```

Likewise:

```text
Power station offline
```

does not confirm:

```text
why it failed.
```

Confirmation must attach to:

```text
THE SPECIFIC CLAIM.
```

---

# 43. Rejection

Aurora may reject a claim when:

```text
strong contradictory evidence exists

source proven false

claim becomes impossible

direct observation disproves it.
```

Rejected claims should not necessarily be:

```text
deleted.
```

They may remain in:

```text
history.
```

---

# 44. Superseded Information

Information may be correct at one time and wrong later.

Example:

```text
10:00
Bridge open.

14:32
Bridge collapses.
```

The earlier record is not:

```text
FALSE.
```

It is:

```text
SUPERSEDED.
```

---

# 45. False Information vs Outdated Information

Aurora must distinguish:

```text
FALSE
```

from:

```text
OUTDATED.
```

Example:

```text
"Bridge open"
at 10:00
```

was true.

At 15:00:

```text
it may be outdated.
```

That does not make the original observation:

```text
incorrect.
```

---

# 46. Staleness

Information becomes stale when:

```text
its age
reduces confidence
that it still describes
the current world.
```

Staleness depends on:

```text
domain volatility.
```

---

# 47. Domain-Specific Freshness

Example:

```text
Mountain location:
changes slowly.

Traffic condition:
changes rapidly.

Hospital fuel:
changes moderately.

Character location:
may change rapidly.

Legal identity:
changes rarely.
```

Therefore one universal:

```text
STALE AFTER X HOURS
```

rule is insufficient.

---

# 48. Freshness Decay

Conceptually:

```text
CONFIDENCE IN CURRENT STATE
↓
AS
INFORMATION AGE
↑
```

But decay speed depends on:

```text
expected volatility.
```

---

# 49. Contradiction

A contradiction exists when Aurora holds:

```text
MULTIPLE INCOMPATIBLE CLAIMS
```

with meaningful support.

Example:

```text
Road Authority:
Bridge open.

Police Unit:
Bridge destroyed.
```

Correct response:

```text
CONTRADICTION ACTIVE.
```

Not:

```text
choose newest blindly.
```

---

# 50. Contradiction Analysis

Aurora should examine:

```text
timestamp

source reliability

source independence

observation directness

data integrity

possible temporal change

possible semantic mismatch.
```

---

# 51. Apparent Contradiction

Not every disagreement is a true contradiction.

Example:

```text
Source A:
Bridge open at 14:00.

Source B:
Bridge destroyed at 14:40.
```

These may both be true.

Therefore:

```text
TIME
```

must be evaluated before declaring:

```text
CONTRADICTION.
```

---

# 52. Semantic Contradiction

Example:

```text
Source A:
Hospital operational.

Source B:
Hospital closed.
```

Possible explanation:

```text
Emergency department:
operational

General admissions:
closed.
```

Aurora should attempt to resolve:

```text
SCOPE
```

before assuming conflict.

---

# 53. Belief Revision

When new evidence arrives:

```text
NEW EVIDENCE
↓
IDENTIFY AFFECTED CLAIMS
↓
COMPARE
↓
UPDATE SUPPORT
↓
UPDATE CONTRADICTIONS
↓
RECALCULATE CONFIDENCE
↓
REVISE BELIEF
↓
PROPAGATE TO DEPENDENT INFERENCES
↓
REASSESS PREDICTIONS
↓
PRESERVE HISTORY.
```

---

# 54. Belief Revision Must Propagate

Example:

```text
OLD BELIEF:
Bridge operational.
```

Used by:

```text
Evacuation Route Prediction

Fuel Delivery Plan

Hospital Supply Estimate.
```

New evidence:

```text
Bridge destroyed.
```

Then Aurora must reconsider:

```text
ALL DEPENDENT ASSESSMENTS.
```

---

# 55. Belief Dependency Graph

Conceptually:

```text
CLAIM A
↓
BELIEF B
↓
INFERENCE C
↓
PREDICTION D
↓
RECOMMENDATION E.
```

If:

```text
CLAIM A
```

changes significantly:

```text
B
C
D
E
```

may require revision.

---

# 56. Belief Revision Is Not Memory Erasure

Old belief:

```text
Bridge likely operational.
```

New belief:

```text
Bridge confirmed destroyed.
```

Aurora should retain:

```text
Previous belief

Previous confidence

Evidence available at the time

Reason for revision.
```

This supports:

```text
AUDITABILITY

LEARNING

CONTINUITY.
```

---

# 57. Evidence Arrival Order

Aurora must not assume information arrives in:

```text
chronological world order.
```

Example:

```text
15:00
Aurora receives report
about event at 13:00.

15:05
Aurora receives report
about event at 12:30.
```

Records must distinguish:

```text
EVENT TIME

OBSERVATION TIME

REPORT TIME

RECEIPT TIME.
```

---

# 58. Late Information

Late information may revise Aurora's understanding of:

```text
PAST EVENTS.
```

Example:

```text
Aurora believed:
power failure began 14:10.

New historical telemetry:
failure actually began 13:52.
```

Aurora may revise:

```text
historical belief.
```

---

# 59. Knowledge of Knowledge

Aurora should maintain awareness of:

```text
HOW WELL IT KNOWS SOMETHING.
```

Example:

```text
Aurora knows:

hospital status
with high confidence

road status
with low confidence

civilian location
not at all.
```

This is:

```text
META-KNOWLEDGE.
```

---

# 60. Unknown Unknowns

Aurora cannot explicitly represent every:

```text
THING IT DOES NOT KNOW
IT DOES NOT KNOW.
```

Therefore the architecture must allow:

```text
SURPRISE.
```

World events may occur outside:

```text
Aurora's current model.
```

---

# 61. Model Surprise

Example:

```text
Aurora predicts:
regional fuel stable.

Unexpected event:
private depot destroyed.
```

Aurora did not know:

```text
the depot had become
a critical dependency.
```

The result should trigger:

```text
MODEL REVISION.
```

Not:

```text
retroactive knowledge.
```

---

Every important Aurora belief should be traceable through:

```text
CLAIM

↓

↓
ORIGIN.
```

Where possible.

If provenance is incomplete:

```text
confidence should reflect that.
```

# 64. Information Lineage

Aurora should distinguish:

```text
ORIGINAL SOURCE
```

from:

```text
REPEATER.
```

Example:

```text
Civilian
↓
social media
↓
news station
↓
government monitoring
↓
Aurora.
```

The existence of:

```text
multiple transmission nodes
```

does not create:

```text
multiple independent observations.
```

---

# 65. Deception

Sources may intentionally provide:

```text
FALSE INFORMATION.
```

Aurora must therefore support:

```text
possible deception

known deception

source compromise

identity spoofing

fabricated evidence.
```

---

# 66. Deception Is Not Automatically Detectable

Aurora should not automatically know:

```text
THIS SOURCE IS LYING.
```

unless evidence supports it.

Instead:

```text
deception
```

may be one hypothesis among others.

---

# 67. Character Statements

A character saying:

```text
"I saw the bridge collapse."
```

creates:

```text
A REPORT.
```

Aurora may consider:

```text
character reliability

location

timing

ability to observe

possible motive

corroboration.
```

But Aurora must not inspect:

```text
Character State
```

to determine whether:

```text
the character is lying.
```

---

# 68. Player Statements

The player is subject to the same epistemic rules.

Player statement:

```text
"The road is clear."
```

becomes:

```text
PLAYER-SOURCED CLAIM.
```

Aurora may trust it strongly.

But:

```text
PLAYER INPUT
≠
WORLD TRUTH.
```

---

# 69. Authority Is Not Infallibility

Official source:

```text
Government Emergency Service
```

may have:

```text
high authority.
```

But authority does not guarantee:

```text
current information

correct information

complete information.
```

Therefore:

```text
AUTHORITY
≠
TRUTH.
```

---

# 70. Consensus Is Not Truth

If many sources agree:

```text
confidence may rise.
```

But Aurora must consider:

```text
shared origin

shared error

shared bias

information cascade.
```

Therefore:

```text
CONSENSUS
≠
CERTAINTY.
```

---

# 71. Historical Reliability

Source trust may evolve through:

```text
previous claims

later outcomes

domain performance

error frequency

correction behavior.
```

Example:

```text
Source X:
excellent weather reporting

poor casualty estimates.
```

Trust should ideally be:

```text
DOMAIN-SENSITIVE.
```

---

# 72. Confidence Update

Conceptually:

```text
PRIOR BELIEF
+
NEW EVIDENCE
+
SOURCE RELIABILITY
+
CORROBORATION
+
CONTRADICTION
+
FRESHNESS
=
```
